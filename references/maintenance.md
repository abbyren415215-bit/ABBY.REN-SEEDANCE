# 项目维护与GitHub同步

远端唯一目标：https://github.com/abbyren415215-bit/ABBY.REN-SEEDANCE.git，默认分支main。用户已明确授权：今后严格按本项目执行，每项工作流更新都上传GitHub。此授权是任务内更新后同步，不是定时后台监控，不需创建自动化。

## 何时同步

- 用户要求修改、修复、合并工作流，或明确确认一条新的永久规则：更新对应权威文件、CHANGELOG和必要的项目状态，然后提交并推送。
- 用户要求保存剧本、提示词、单集设定、对白、分段进度或素材使用记录：默认保存到工作目录本地剧本资料，标清草稿、已确认、已生成；“保存”不等于授权GitHub公开。只有明确要求上传这些具体内容时才另行同步。第八集已明确仅本地，不再写入仓库正文、摘要或更新日志。
- 仅在聊天讨论、解释或产出未确认提示词：不自动生成文件或上传。只要文字/禁止工具的明确要求优先，本轮不能执行Git；若本轮还要求持久化，注明待同步，不假称已上传。
- 图片、音色、成片、凭据及机器专用配置不因文字工作流维护授权而上传；新增这类范围须有对应明确要求。

## 权威文件与工作目录接入

- 仓库根SKILL.md是唯一工作流入口，AGENTS.md负责持续执行与维护约束。
- projects/bingbing/workflow.md：通用制作方式；current-state.md：公开范围说明与既有记录，不再自动收录新剧本进度；series-bible.md：公开通用设定；production-protocol.md：稳定生成协议。具体剧集状态优先在工作目录本地剧本资料中维护。
- 本地剧集目录AGENTS.md使用integrations/bingbing/AGENTS.md中的接入规则。在其他机器安装时按实际技能路径解析，不把个人绝对路径写进公开文件。
- 本地固定设定档和稳定协议继续维护：通用规则与仓库对应文本同步，本地独有的剧本、当集造型和素材状态不得机械复制到公开版本。本地与公开副本可以因保存范围不同而有明确差异，不以“镜像一致”为由上传私有剧情。
- 会话新决定经用户确认后，先分流为通用规则或本地剧本事实，再决定保存位置；不能用时间戳覆盖语义差异，也不能把已确认剧情自动当成已授权公开。
- 安装目录与GitHub共同使用同一Git仓库，避免再次形成两套无关联历史。若存在额外安装副本，本次任务检查并更新相关副本，而不是让用户依赖旧聊天记忆。
- 已安装旧技能的ABBY专用路由见[integrations/legacy-routing.md](../integrations/legacy-routing.md)。来源快照的SKILL.source.md只供查阅，不能改回SKILL.md后再次被发现为同名执行入口。

## 每次更新的完成条件

1. 读取git status、remote、当前分支与相关diff，确认目标仓库；fetch远端并比较新提交。保留既有本地修改，不用git add .混入不相关文件。
2. 修改权威规则与必要引用，记录变更来源、适用范围、废止的旧默认值。上游更新固定到明确提交，保留原文与署名，在覆盖规则中裁决冲突。
3. 核对链接、文件路径、技能frontmatter、工作目录入口与关键制作约束；脚本改动才运行相应测试。实际平台参数未核实时不得改写成官方保证。
4. 只暂存本次明确文件，检查staged diff中没有照片、音频、视频、凭据、个人绝对路径或未授权公开的剧本/对白/单集摘要。commit后正常push到origin/main；远端有新提交先安全合并，冲突需按内容解决，不force push。
5. 核验git rev-parse HEAD与git ls-remote origin refs/heads/main一致，工作树检查清楚；给用户简短说明更新内容和提交链接。

如果网络、认证或远端冲突导致失败，保留本地提交并明确“已本地保存、尚未同步”，说明实际阻碍；不把计划提交或缓存origin/main当作远端成功证据。失败后只在有新信息时重试。

终端缺少凭据但GitHub连接器已授权时，可用GitHub Git Data API上传已核验的完整文件树，以远端最新提交为父节点创建提交，并非强制更新main。更新ref前再次核对远端未变化；变化则重新合并，不覆盖远端新增内容。API提交SHA可能与本地不同：先核对树SHA相等，再将原本地分支改名保留，fetch后从远端建立跟踪main；不reset、不删除本地历史。最终仍要求本地HEAD与远端main一致。
